### Introduction
A **Graphics Processing Unit (GPU)** is a processor whose design emphasizes performing *large amounts* of *parallel work*. GPUs began as specialized hardware for real-time graphics, then gained programmable graphics stages. **NVIDIA** introduced **CUDA** in 2006 so programmers could use GPU throughput for general computation without expressing the work as graphics operations.

CUDA, originally expanded as Compute Unified Device Architecture, now names NVIDIA's broader heterogeneous-computing platform: its GPU programming models, software interfaces, compiler toolchain, libraries, and supporting hardware features. A GPU is the physical processor; CUDA is the platform through which software uses compatible NVIDIA GPUs.

> Although we focus primarily on CUDA in this course, GPU programming is broader than CUDA. Other options include AMD's HIP, Apple's Metal, and cross-platform standards such as SYCL, OpenCL, Vulkan compute, and OpenMP target offloading. SYCL is a Khronos standard, with implementations including Intel's toolchain; HIP supports targeting both AMD and NVIDIA GPUs.
{: .prompt-info }

#### What is a Processor Doing?
- The journey of any software starts at a human-written (or AI written nowadays, sigh) source code, which then a **compiler** translates into *lower-level representations* that a *target machine* / a later compiler stage can execute / translate further. 
- Post compilation much of the work is represented as **instructions**: basic core operations such as:
    - `load a value from memory` / `add two values` / `compare` / `branch` / `store a result`
  
  The values an instruction operates on are called its *data*.
- A **processor** then is the hardware that repeatedly obtains such instructions, determines what they mean, obtains their input data, performs the operation and records the result.
    - To make the process more efficient, real-world processors overlap the processing of multiple instructions, even within a single instruction stream, and may execute multiple operations at once.
    - An **instruction stream** is defined as the ordered sequence of instructions followed by one executing programming context.
    - An *instruction stream* combined with the execution context (registers / stack / program counter) is referred to as a **Thread**.
- **CUDA** threads tend to be much more **lightweight** and **numerous** than **CPU** threads, to unlock **massive parallelism** as we will shortly discuss.

The processor cannot do useful work without storage:
- **Registers** hold a small number of values immediately used by execution hardware
- **Memory** holds much more code and data, but access usually takes longer
- **Caches** are intermediate storage that try to keep recently or nearby used memory closer to the processor (faster access as compared to memory)

#### Latency vs Throughput
It's important for us to establish the difference between these terms as they usually don't come hand in hand, and may need dedicated optimizations.
- **Latency** is how long one task or operation takes from start to finish
- **Throughput** is how much total work finishes per unit time. A system can have high latency and still achieve high throughput by overlapping work on multiple tasks.

An example to illustrate the above: Suppose a sports car delivers one passenger in 20 minutes, while a bus delivers 40 passengers in 60 minutes. The car has lower trip latency (20 vs 60 minutes), but the bus has higher average throughput over its trip (40 vs 3 passengers per hour). Neither is universally “faster”, they optimize different measures.

A **modern CPU** is primarily designed to **minimize** the **latency** of a **few complicated instruction streams**:
- It uses large caches and sophisticated control hardware: it predicts which branch a program will take, speculatively begins likely future work, and may execute independent instructions out of their original order while preserving the program's result.

A **GPU** is primarily designed to **maximize throughput** when the *same broad operation* can be applied to a *great deal of data*.
- It devotes much more of the chip to arithmetic hardware and maintains many threads so that useful work can continue while other work waits (for data to be fetched from memory for example).

These are design tendencies, not exclusive capabilities: CPUs also pursue throughput, and GPUs also use caches and instruction-level parallelism.

> A GPU is not simply “a CPU with more cores.” Its processing units, scheduling strategy, cache balance, synchronization model, and intended kind of parallel work differ. Even the word core is ambiguous in GPU discussions. We will shed more light on this as we deep dive into the GPU Architecture.
{: .prompt-warning}

#### Optimizing for vs Hiding Latency
As the designs of the processors differ, so does the design (approach) to a solution for a given problem.
- A **latency-oriented processor (CPU)** tries to reduce the time until dependent instructions can execute, predict what comes next, and find independent instructions from the same thread's instruction stream to execute in the meantime. It further utilizes large data caches to speed up accesses to recently or nearby used data.
- A **throughput-oriented processor (GPU)** also utilizes caches, but relies heavily on having lots of independent work. While some work waits for data from memory, the GPU can make progress on other work that is ready to run. This **hides latency**: it does not make the memory access itself faster, but keeps the processor busy during the wait. Simply adding more threads does not help if they all need to wait for the same earlier result, so highly sequential tasks might not benefit a lot from this approach.

#### Concurrency vs Parallel Execution vs Available Parallelism
These related terms distinguish overlapping tasks, simultaneous execution, and opportunities for simultaneous execution:
- **Concurrency** means multiple tasks have overlapping lifetimes; their execution may be interleaved or simultaneous. A single CPU core can support concurrency.
- **Parallel execution** means multiple operations physically execute at the same time.
- **Available parallelism** is the amount of work that could execute simultaneously, given sufficient hardware and satisfied dependencies.

#### Host & Device
As we established, CUDA identifies NVIDIA's heterogeneous computing platform (a system containing unlike processors) consisting of CPUs and NVIDIA GPUs.

An application's journey:
- *Begins* on the **CPU**, and uses the **GPU** for selected parts whose parallelism makes the acceleration worthwhile (as discussed, this acceleration doesn't work well for highly sequential tasks)
- The **CPU** and the *memory directly associated with it* are called **Host** & **Host Memory**, further the code running on the CPU is called **Host Code**. It prepares data, allocates memory, requests transfers across **Host** & **Device** (will be defined just below), and consumes results
- The **GPU** and the *memory directly associated with it* are called **Device** & **Device Memory**
  - **Device Code** executes on the GPU
  - A **GPU** entry function launched by the host is historically called a **Kernel**
    - **Launching a Kernel (GPU function/program)** means requesting the Device (GPU) to execute a logical sequence of instructions many times in parallel, where each logical execution is a **CUDA Thread**.
    - A **CUDA Kernel**, unlike an ordinary CPU function, is not executed and waited on for a result by the CPU; instead, the launch normally queues device work and returns control to the CPU.
      - (yes we can await completion and result, we'll discuss it as we discuss more)

The host and device may be:
- on separate chips connected by an **interconnect**: a physical link that transports **commands** and **data**, commonly via PCI Express (PCIe),
- on a system-on-chip, sharing a package and physical memory

Irrespective, CUDA still uses host/device roles.

Host code requests device-targeted operations such as memory allocation, data transfer, kernel launch, synchronization, and other Device (GPU) services via the **CUDA API**.

> Because kernel launches (and asynchronous data operations) do not block the host, CPU host code and GPU device code can execute at the same time. *High-performance applications try to keep both processors useful while respecting data dependencies*; **"offloading to the GPU"** *does not require the CPU to remain idle*.
{: .prompt-tip }

Consider an example of vector addition:
- The CPU creates two input arrays `A` and `B` (and an output array `C`), makes them accessible to the GPU, and launches an addition kernel.
- CUDA creates many logical threads (in this case one per index, however note that optimizations may include clubbing multiple index operations into one call considering architectural limitations, we'll discuss more on this later)
- Each thread `t` computes `C[t] = A[t] + B[t]`
- The CPU later waits for completion and copies `C` back from device to host memory.

GPUs are specialized for highly parallel computations and devote more transistors to data processing units, while CPUs dedicate more transistors to data caching and flow control. Figure 1 shows an example distribution of chip resources for a CPU versus a GPU.

### Dissecting the GPU
A **chip** is a physical piece of silicon containing electronic circuits (bear with me, we'll build up from basics, feel free to skip this on exam day :p). Its smallest elements are transistors; chip designers combine transistors into storage, control logic, arithmetic units, and communication networks. However, "more transistors" does not by itself mean a better-performing chip; the important question is what they are used for.

Let's define a few memory-related terms:
- **DRAM** is the large-capacity working memory used for arrays and other program data.
- **Memory Controllers** move data between DRAM and the GPU.
- A device-wide **L2 Cache** sits between memory controllers and the processing units, so frequently used memory may be served without returning to DRAM.

#### Streaming Multiprocessors
A GPU chip consists of many processing units called **Streaming Multiprocessors**, abbreviated **SMs**. To organize a large chip, NVIDIA groups *several* **SMs** and their associated cluster-level hardware into a **Graphics Processing Cluster**, abbreviated **GPC**.

> Most ordinary CUDA kernels do not explicitly address GPCs. GPC placement becomes visible when using a thread-block cluster: an optional software grouping whose blocks are guaranteed to be co-scheduled within one GPC.
{: .prompt-info}

Thus, an SM is the GPU's main general-purpose execution engine. Execution of a kernel from an SM's perspective:
- CUDA assigns an SM **thread blocks** (a slice of threads belonging to a kernel launch defined by the programmer).
- The **SM** further executes each block as fixed groups of **32 threads** called **Warps**.
- The **SM** keeps many warps' state resident, chooses ready warps, and issues their instructions to its arithmetic, load/store, special-function, and other execution units.
  - It also owns a register file and configurable on-chip data storage (we develop this further in a future section)

As established, an **SM** is not one giant arithmetic unit. It is a coordinated collection of resources:
- The **register file** is a large on-chip bank of registers. The compiler gives each active CUDA thread some registers for its private variables. Because all resident threads draw from a finite file, high registers-per-thread can reduce how many threads fit simultaneously.
- **Warp schedulers** examine resident warps and choose those whose next instruction is ready.
- A **scoreboard** tracks dependencies. If an instruction needs a value that has not arrived, that warp is not ready for that instruction.
- **Functional units** execute particular kinds of operations: integer arithmetic, floating-point arithmetic, load/store address work, special mathematical functions, tensor/matrix work, and more. The exact mixture varies by architecture.
- The **unified data cache** supplies physical on-chip storage that can serve as hardware-managed L1 cache and programmer-managed shared memory. The balance can be configurable.
- **Instruction fetch/decode hardware** obtains and interprets instructions for warps. **Instruction caches** reduce repeated fetching from farther memory.

> The SM’s register file is one physical storage resource, but registers are logically private per thread. Shared memory is also physically inside the SM, but it is logically shared by the threads of a block. Physical location and programming visibility are different ideas.
{: .prompt-warning}

Before we continue further, let's clear a common misconception. GPU product descriptions often publish a count of "CUDA cores"; this in fact refers to the small functional units capable of executing specific types of instructions. It is **not** comparable to a CPU core, which is capable of independently running full instruction streams.

For reasoning about CUDA scheduling, as you would during this course, we use the following terms:
- **SM** for the processor-like hardware unit that receives blocks and schedules warps.
- **Warp** for a hardware execution group of 32 CUDA threads.
- **Lane** for one *thread position* within that warp-wide instruction.
- **Functional unit** for the hardware that performs a particular operation.

> **Q. Why can an SM hold more threads than it can execute at once?**
>
> The answer to this essentially boils down to latency hiding: the scheduler swaps between warps stalled waiting for data or dependencies and issues a ready instruction from another warp. Because every resident warp's state already has its own allocated slice in the SM's register file, switching warps does not require saving and restoring registers to off-chip memory—making the switch overhead nearly zero. (How many threads/warps an SM can keep resident—often discussed as **occupancy**—is bounded by hardware limits on warps/blocks per SM as well as per-kernel resource usage like registers per thread and shared memory per block.)
{: .prompt-info}

> While we discuss a stable CUDA programming model: System $\rightarrow$ GPU Device $\rightarrow$ GPCs $\rightarrow$ SMs $\rightarrow$ warp schedulers + execution lanes $\rightarrow$ functional resources, it's important to note that a real product may vary in physical routing / partitions / issue width / cache organization and internal execution. Our focus stays centered around the CUDA programming model in this course.
{: .prompt-warning}

**Now that we have clarity on an SM, let's trace an instruction's path through it:**
- Each resident warp has its own logical *program counter* and *execution state*.
- The *instruction fetch/decode* path obtains the *warp's next instruction*.
- A *scoreboard* marks the warp ready for execution only when the required source operands and resources are ready for its current stage.
- A *warp scheduler* issues the instruction to matching functional units: integer, FP, load/store, special-function, tensor, etc.
- *Active lanes* perform the operation; masked lanes do no useful work for that instruction (we haven't discussed this yet, but we shortly will in detail!).
- Results are written to registers or memory. Another ready warp can issue while a previous warp waits on a long-latency operation.
